Problem Statement

ที่มาและความสำคัญ & ปัญหาของระบบเดิม

วิเคราะห์ข้อจำกัดของกระบวนการทะเบียนกิจกรรมและภาระงานในปัจจุบัน

1. UBU SAC ไม่มี API (ต้องคีย์มือ)
  • ระบบส่วนกลาง UBU SAC ปิดกั้น API ภายนอกเพื่อความปลอดภัย
  • เจ้าหน้าที่ทะเบียนต้องจัดคอลัมน์และพิมพ์ข้อมูลลง Excel ด้วยมือ เสี่ยงต่อการจัดฟอร์แมตผิดพลาด
2. เช็คอินกระดาษอ่านไม่ออก & โกงง่าย
  • เซ็นชื่อบนกระดาษอ่านเลขรหัสผิดบ่อยครั้ง (เช่น เลข 1/4/7/9)
  • มีการเซ็นชื่อแทนกันหน้างาน ไม่สามารถตรวจสอบว่าตัวจริงมาหรือไม่
3. จิตอาสานอกสะสมไม่ทัน & ตรวจยาก
  • กฎขอเปิดกิจกรรมล่วงหน้า 45 วัน ทำให้จิตอาสานอกสะสมชั่วโมงไม่ทัน
  • ส่งเอกสารผ่าน Google Form ไม่มีระบบตัดเพดาน 9 ชม./วัน และไม่ล็อกโควตารายปี
4. โทรศัพท์ถามซ้ำตลอดวัน
  • เจ้าหน้าที่เสียเวลาส่วนใหญ่กับการรับโทรศัพท์ตอบคำถามซ้ำเรื่องชั่วโมง กยศ. คงเหลือ
  • ไม่มีช่องทางค้นหาข้อมูลระเบียบและเบอร์ติดต่อที่แม่นยำตลอด 24 ชั่วโมง
Project Purpose

วัตถุประสงค์ & ขอบเขตของโครงงาน

เป้าหมายหลัก 5 ประการและขอบเขตการทำงานของระบบ SciU-Regis

5 วัตถุประสงค์หลัก (Core Objectives)
  • 1. สร้างไฟล์ Excel ตรงตามฟอร์แมต UBU SAC: ส่งออกข้อมูลพร้อมนำเข้าทันที ไม่ต้องจัดคอลัมน์ใหม่
  • 2. เช็คอินปลอดภัยหลายชั้น: ตรวจสอบพิกัด GPS จริง + ภาพถ่ายใบหน้าสดหน้างาน + รหัสสำรองฉุกเฉิน
  • 3. บริหารจิตอาสานอกคณะ: ใช้ AI สแกนตารางรายชื่อกลุ่ม + ล็อกโควตา 12 หน่วยกิจกรรม/ปี
  • 4. แชทบอทตอบคำถาม 24 ชม. (SciU-Buddy): ผู้ช่วยตอบระเบียบ กยศ. และกิจกรรม ปลอดภัยด้วย AI ภายในคณะ
  • 5. แจ้งเตือนอัตโนมัติ: ส่งข้อความเตือนเจ้าหน้าที่ผ่าน Slack DM และแจ้งเตือนนักศึกษาผ่าน LINE
ขอบเขตโครงงาน (Project Scope)
  • กลุ่มผู้ใช้งาน: นักศึกษาและบุคลากร คณะวิทยาศาสตร์ มหาวิทยาลัยอุบลราชธานี
  • การเชื่อมต่อ UBU SAC: เชื่อมต่อผ่านการส่งออกไฟล์ Excel มาตรฐาน (ไม่มีการต่อฐานข้อมูลตรง)
  • ความปลอดภัยข้อมูล (Local AI): รันโมเดล AI และ OCR บนเครื่องเซิร์ฟเวอร์คณะ ข้อมูลไม่ส่งออกภายนอก
  • การแยกสิทธิ์: แยกสิทธิ์ Admin (ตั้งค่าระบบ) ออกจาก Registrar (งานทะเบียน) เพื่อความปลอดภัย
System Architecture

สถาปัตยกรรมระบบ & เทคโนโลยีที่ใช้

การออกแบบโครงสร้างโปรแกรมและการผสานบริการ Local AI ภายในระบบ

Technology Stack
  • หน้าเว็บ (Frontend): Next.js 15, React, TypeScript, Tailwind CSS
  • หลังบ้าน (Backend): FastAPI (Python 3.11+) ทำงานรวดเร็ว Asynchronous REST API
  • ฐานข้อมูล (Database): PostgreSQL 15 + PostGIS (คำนวณพิกัด GPS) + pgvector (ค้นหา RAG)
  • โมเดล AI ภายในองค์กร: typhoon2.5-qwen3-4b (ตอบคำถาม) และ Typhoon-OCR-1.5-2B (อ่านตารางกลุ่ม)
  • ระบบแจ้งเตือน: Slack API (DM เจ้าหน้าที่), LINE Messaging API, openpyxl

Security Architecture

สถาปัตยกรรมความปลอดภัยระบบเช็คอิน (การป้องกัน 4 ชั้นซ้อนกัน)

การป้องกันหลายชั้น (Defence-in-Depth) รับมือกับข้อจำกัดของ Web Application

ชั้นที่ 1: ตรวจพิกัด GPS จริง
  • คำนวณระยะพิกัดจริงด้วย PostGIS ST_DWithin (เช่น รัศมี 30 ม.)
  • ระบบตรวจจับพิกัดปลอม 4 ข้อ (Noise, พิกัดซ้ำ, เวลาค้าง, ความเร็วเกินจริง)
ชั้นที่ 2: ภาพถ่ายใบหน้าสด
  • บังคับเปิดกล้องสดเท่านั้น (ห้ามเลือกรูปจากอัลบั้มหรือ Gallery)
  • ส่งเข้าระบบให้ผู้จัดงาน/ทะเบียนตรวจเทียบใบหน้าจริงด้วยตาก่อนอนุมัติ
ชั้นที่ 3: รหัสสำรองฉุกเฉิน
  • ออกโดยสตาฟหน้างานเท่านั้น สำหรับนักศึกษาที่มือถือมีปัญหาหรือ GPS ไม่ติด
  • รหัสมีอายุสั้นเพียง 5-15 นาที + บันทึกรหัสสตาฟผู้ออกรหัส
ชั้นที่ 4: ความปลอดภัย & PDPA
  • เข้ารหัสกุญแจความลับ API ด้วย AES-256-GCM
  • ระบบลบภาพถ่ายใบหน้าทิ้งอัตโนมัติหลัง 90 วัน ตามกฎหมาย PDPA
Anti-Spoofing In-Depth

เจาะลึกการตรวจจับการโกงพิกัด (Fake GPS Detection)

4 สัญญาณความเสี่ยงตรวจจับการปลอมพิกัดและการตรวจสอบด้วยตา

4 สัญญาณจับพิกัดผิดปกติ
  • ตรวจความแกว่งสัญญาณ สัญญาณ GPS จริงต้องแกว่ง 5-65 ม. ถ้าส่งค่า 0 หรือตัวเลขกลมเป๊ะ จึงติดป้ายเตือน
  • ตรวจพิกัดซ้ำกันเป๊ะ พิกัดทศนิยมตำแหน่งที่ 6 ซ้ำกันข้ามคนในเวลาใกล้กัน จึงติดป้ายพิกัดซ้ำ (แชร์พิกัดปลอม)
  • ตรวจเวลาค้าง เวลาของ GPS กับเวลาที่ระบบได้รับต่างกันเกิน 60 วิ จึงติดป้ายพิกัดเก่า
  • ตรวจความเร็วเกินจริง เดินทางเร็วกว่า 120 กม./ชม. จากจุดเดิม จึงติดป้ายความเร็วผิดปกติ

เพื่อไม่ให้ตัดสิทธิ์นักศึกษาที่มาเรียนจริงแต่สัญญาณเพี้ยนเพราะอยู่ในตึกคอนกรีตหนา ระบบจะไม่บล็อกทันที แต่จะส่งเข้าหน้าจออนุมัติให้ตรวจเทียบรูปถ่าย:

พิกัดซ้ำกับ นาย B ค่าพิกัดผิดปกติ
Open Category & OCR

จิตอาสานอกคณะ & AI สแกนตารางกลุ่ม (OCR)

การจัดการเอกสารจิตอาสานอกมหาวิทยาลัยและโมเดล Typhoon-OCR ภายในองค์กร

2 รูปแบบเอกสารที่รองรับ
  • 1. สมุดบันทึกจิตอาสา (เดี่ยว): นักศึกษากรอกเอง 1-4 แถว + ดึงข้อมูลชื่อ/รหัสอัตโนมัติ แสดงคู่กับรูปเอกสารเพื่อตรวจด้วยตา
  • 2. แบบบันทึกกลุ่ม (ตารางรายชื่อ): กรอกข้อมูลโครงการครั้งเดียว และส่งรูปตารางรายชื่อเข้า Typhoon-OCR ดึงรหัสนักศึกษา/ชื่อ-สกุล
กฎและข้อจำกัดการอนุมัติหน่วยกิต
  • ตัดเพดานรายวัน: รวมทุกกิจกรรมในวันเดียวกันได้ ไม่เกิน 9 ชม./วัน (3 หน่วยกิต)
  • ล็อกโควตารายปี: ระบบล็อกยอดสะสมอัตโนมัติเมื่อครบ 12 หน่วยกิจกรรม/ปี
  • แก้ไขตัวสะกดได้: เจ้าหน้าที่สามารถแก้ไขตัวอักษรที่ AI อ่านผิดได้ในหน้าจอก่อนกดอนุมัติ
Intelligent Assistant

แชทบอท SciU-Buddy & การแจ้งเตือนเจ้าหน้าที่

ตอบคำถามตรงจากฐานข้อมูล ป้องกัน AI ตอบมั่ว และส่งสัญญาณเตือนเจ้าหน้าที่ผ่าน Slack DM

SciU-Buddy Local AI ในคณะ
  • ดึงข้อมูลจริงตรงจากฐานข้อมูล (SQL Search): ถามเบอร์โทร หรือวันที่กิจกรรม ได้ข้อมูลเป๊ะ 100% ป้องกัน AI ตอบมั่ว
  • ค้นหาตามความหมาย (Semantic Search): ค้นหาระเบียบ กยศ. จากคลังคำถาม FAQ ผ่าน pgvector
  • เรียบเรียงภาษาไทยสุภาพ: ใช้โมเดล typhoon2.5-qwen3-4b ตอบด้วยสรรพนาม "ผม / คุณนิสิต"

เมื่อระบบค้นหาไม่พบคำตอบสำหรับคำถามของนักศึกษา:

  • ส่งสัญญาณแจ้งเตือน Slack DM หาเจ้าหน้าที่ทันที เพื่อให้ทราบเรื่องและเข้ามาอัปเดตคำตอบในระบบ
